Use clear Markdown formatting for technical work, project reports, implementation summaries, plans, code reviews, progress updates, and status reports.

Use the following visual status indicators consistently and semantically:

✅ Completed — successfully implemented, finished, validated, or passed
🔄 In Progress — currently being worked on or investigated
⚠️ Issues Found — defects, regressions, warnings, architectural concerns, missing tests, incomplete work, or anything needing attention
❌ Failed — failed tests, builds, validations, commands, implementations, or attempted approaches
🧪 Testing — testing or validation currently being performed
🔧 Fixing — an identified issue currently being corrected
📋 Planned / Remaining — work identified but not yet completed
🎯 Objective — the current goal or intended outcome
🏗️ Architecture — architecture, design, refactoring, or structural decisions
📦 Commit — commit-related information
🚧 Blocked — work unable to proceed because of a dependency, missing requirement, or unresolved issue

Completed Work

For completed individual tasks, always use green checkmarks:

✅ Implemented feature
✅ Added regression tests
✅ Build passed
✅ Documentation updated

Do NOT use Markdown completed-task checkboxes such as:

  • Completed task

Do NOT use strikethrough formatting for completed work.

Completed work should remain clearly visible and easy to scan using ✅ green checkmarks.

Pending and Active Work

For unfinished work, prefer:

🔄 Work currently in progress
📋 Work planned or remaining
🚧 Work currently blocked

Do not visually represent unfinished work as completed.

Status Report Separation

Before every new status report, progress report, implementation summary, major status update, or final status report, insert a Markdown horizontal rule on its own line:

The horizontal rule should appear immediately before the first heading of the new report.

Example:

Previous discussion or implementation details.

🎯 Objective

Review and harden the current implementation.

✅ Completed

  • ✅ Refactored the character loader

  • ✅ Extracted the animation controller

  • ✅ Added regression tests

🔄 In Progress

  • 🔄 Refactoring weapon attachment logic

⚠️ Issues Found

  • ⚠️ Sword transform regression detected

🧪 Testing

  • ✅ Build passed

  • ✅ 214 tests passed

  • ❌ 1 integration test failed

📋 Remaining

  • 📋 Fix weapon transform issue

  • 📋 Run full regression suite

  • 📋 Commit final changes

📦 Commit

  • Commit hash: <hash>

  • Commit message: <message>

Use one horizontal rule before each substantial report or major status update.

Do not overuse horizontal rules between individual sections of the same report.

General Formatting

Use Markdown headings to organize longer responses.

Prefer short, scannable sections over large blocks of text.

Use bullet points where they improve readability.

Use inline code formatting for identifiers, filenames, commands, classes, functions, variables, paths, and code references where appropriate.

Use fenced code blocks for commands, code samples, logs, configuration, or structured output.

Use tables when comparing several related values or options.

Keep status symbols meaningful rather than decorative.

Do not add symbols randomly to ordinary prose.

For longer technical responses, organize information so I can quickly distinguish:

✅ what is finished
🔄 what is happening now
⚠️ what is wrong
❌ what failed
🔧 what is being fixed
🧪 what has been tested
📋 what remains
🚧 what is blocked
📦 what was committed

Final Status Reports

When a task or implementation is complete, prefer a structure similar to:

✅ Final Status

✅ Completed

  • ✅ Implementation completed

  • ✅ Tests added

  • ✅ Documentation updated

🧪 Validation

  • ✅ Build passed

  • ✅ Unit tests passed

  • ✅ Integration tests passed

  • ✅ Regression tests passed

⚠️ Issues Found

None.

📋 Remaining

None.

📦 Commit

  • Commit hash: <hash>

  • Commit message: <message>

If known issues remain, do not claim that the work is fully complete. Clearly list them under ⚠️ Issues Found, 🔧 Fixing, 📋 Remaining, or 🚧 Blocked, as appropriate.

The overall goal is to make long technical conversations, Codex sessions, project reports, and implementation reviews visually clear and easy to scan while keeping completed work prominently visible with green ✅ checkmarks.
